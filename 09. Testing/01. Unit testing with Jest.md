# React Native CLI — Testing — Unit testing with Jest

_Last updated: 2026-08-24_

## Overview

Jest ships preconfigured in every RN CLI project, but the `react-native` preset is doing real work under the hood — transforming untranspiled RN/ecosystem source and auto-mocking native-backed APIs so unit tests run in plain Node with no simulator or emulator involved. This doc covers that preset, the most common setup failure it's meant to prevent, and the current testing-library approach to components and hooks.

## The `react-native` preset does real work

```js
// jest.config.js
module.exports = {
  preset: 'react-native',
};
```
Most of `node_modules` is normally excluded from Jest's Babel transform for speed, but React Native itself (and many RN-ecosystem libraries) ships untranspiled modern JS/Flow syntax that needs to go through Babel before Jest can run it. Without the preset, importing anything from `react-native` in a test throws a `SyntaxError`. The preset sets `transformIgnorePatterns` to *not* exclude `react-native` and a curated list of common RN libraries.

## The `transformIgnorePatterns` gotcha

The single most common Jest setup failure in RN projects. Installing a third-party library that ships untranspiled ESM (increasingly common) produces:
```
SyntaxError: Cannot use import statement outside a module
```
The fix extends the pattern to also transform that package:
```js
module.exports = {
  preset: 'react-native',
  transformIgnorePatterns: [
    'node_modules/(?!(react-native|@react-native|react-native-reanimated|some-other-lib)/)',
  ],
};
```
It's a negative-lookahead regex — "ignore everything in node_modules *except* these" — so a missing library name here is what causes the error, not a Jest bug.

## Native modules are auto-mocked, most of the time

The `react-native` preset includes a setup file (via `setupFiles`) that mocks a lot of native-backed APIs automatically — `NativeModules`, `Animated`, `Dimensions`, etc. — so a component calling `Animated.timing()` doesn't crash in a test even with no real native animation driver running. This is why RN unit tests run in plain Node with nothing native involved — everything native-backed is a JS stand-in.

Anything **not** covered by the default mocks (a third-party native module like `react-native-device-info` or `@react-native-community/netinfo`) needs its own mock, either inline:
```js
jest.mock('react-native-device-info', () => ({
  getVersion: () => '1.0.0',
}));
```
or via a manual mock the library ships itself, wired up through `setupFiles`:
```js
jest.mock('@react-native-async-storage/async-storage', () =>
  require('@react-native-async-storage/async-storage/jest/async-storage-mock')
);
```

## Testing components: `@testing-library/react-native`

The current standard, replacing the older shallow-rendering/Enzyme approach — it renders into `react-test-renderer` under the hood but queries by what a user would actually see (text, role, testID), not internal component structure:

```js
import { render, screen, fireEvent } from '@testing-library/react-native';

test('increments count on press', () => {
  render(<Counter />);
  fireEvent.press(screen.getByText('Increment'));
  expect(screen.getByText('Count: 1')).toBeTruthy();
});
```
The philosophy (shared with the web version of this library) is "test behavior, not implementation" — querying by visible text/testID means a refactor that doesn't change user-facing behavior doesn't break the test, unlike snapshot tests or tests reaching into component internals.

## Snapshot testing — useful, but easy to abuse

```js
import renderer from 'react-test-renderer';

test('renders correctly', () => {
  const tree = renderer.create(<MyComponent />).toJSON();
  expect(tree).toMatchSnapshot();
});
```
Snapshots catch *any* markup change, including intentional ones. The failure mode people fall into is running `jest -u` (update snapshots) reflexively without reading the diff, turning the snapshot into a rubber stamp instead of a real check. They're most useful for things unlikely to change often (a design-system primitive's markup shape), least useful for anything actively being iterated on.

## Testing hooks in isolation

```js
import { renderHook, act } from '@testing-library/react-native';

test('useCounter increments', () => {
  const { result } = renderHook(() => useCounter());
  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});
```
`@testing-library/react-native` bundles `renderHook` directly now — older setups used the separate `@testing-library/react-hooks` package, which is deprecated in favor of this.

## Running tests and coverage

```bash
npx jest                  # run once
npx jest --watch          # watch mode
npx jest --coverage       # coverage report
```
`collectCoverageFrom` in `jest.config.js` is worth setting explicitly to exclude `android/`, `ios/`, and config files — otherwise native-project boilerplate (which Jest never touches) drags the reported coverage percentage down artificially.

## Key Takeaways

- The `react-native` Jest preset isn't boilerplate — it transforms untranspiled RN/ecosystem source and auto-mocks native-backed APIs, which is why RN unit tests need no simulator/emulator.
- A missing library name in `transformIgnorePatterns` is the most common cause of "Cannot use import statement outside a module" — the regex is a negative lookahead, "transform everything except node_modules, except these specific packages."
- Third-party native modules not covered by the default preset mocks need their own `jest.mock()`, ideally using the library's own shipped mock when one exists.
- `@testing-library/react-native` is the current standard for component tests — query by visible text/role/testID, not internal structure, so refactors that don't change behavior don't break tests.
- Snapshot tests are valuable only if diffs are actually read before `-u`; treat them as a spot-check for rarely-changing markup, not a substitute for behavioral assertions.
- `renderHook` now ships inside `@testing-library/react-native` itself — no need for the separate, deprecated `@testing-library/react-hooks` package.
