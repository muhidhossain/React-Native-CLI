# React Native CLI — Testing — E2E testing with Detox and Maestro

_Last updated: 2026-08-24_

## Overview

Unlike Jest unit tests, which mock everything native and run in plain Node, E2E testing builds the real app and drives it on an actual simulator/emulator or device — catching things unit tests structurally can't, like a broken native build or a permission dialog blocking a flow. This doc covers the two dominant RN E2E tools, Detox and Maestro, which take opposite approaches to the same core problem: reliably synchronizing test steps with a running app.

## Detox — gray-box, synchronization-aware

Detox is built specifically for React Native and hooks into the app's internals to solve the classic E2E flakiness problem: **synchronization**. Traditional E2E frameworks fight timing — a tap needs to wait for animations, network calls, and JS thread work to settle before the next assertion is safe, and naive `sleep()` calls make tests slow and still flaky.

```js
describe('Login flow', () => {
  it('should log in successfully', async () => {
    await element(by.id('email-input')).typeText('user@test.com');
    await element(by.id('password-input')).typeText('password123');
    await element(by.id('login-button')).tap();
    await expect(element(by.text('Welcome'))).toBeVisible();
  });
});
```

Detox hooks into the app's own event loop, animation scheduler, and network layer to know when the app is actually idle before proceeding — no explicit waits needed for most cases. This requires deeper native integration:

- A native test framework component (a Detox pod on iOS, a Gradle dependency on Android) built into a special **test build variant** of the app — not the same binary shipped to users.
- Setup config in `.detoxrc.js` naming the build command, binary path, and simulator/emulator/device target per configuration.
- Because it needs this native hook, Detox is tied specifically to Android/iOS builds of React Native apps — it's not a general mobile automation tool.

## Maestro — black-box, YAML-driven

Maestro takes the opposite philosophy: no native integration, no code, just YAML flows driving the app like a real user, using OS-level accessibility APIs instead of hooking into the app's internals:

```yaml
appId: com.myapp
---
- launchApp
- tapOn: "Email"
- inputText: "user@test.com"
- tapOn: "Password"
- inputText: "password123"
- tapOn: "Log In"
- assertVisible: "Welcome"
```

Because it drives the app the same way regardless of platform, it's much faster to set up — no test-variant build config, no native pod/Gradle wiring. Its synchronization is closer to "smart polling with retries" (including built-in commands like `waitForAnimationToEnd`) than Detox's actual event-loop awareness, so timing-sensitive flows can occasionally need explicit waits Detox wouldn't need.

## The core tradeoff

| | Detox | Maestro |
|---|---|---|
| Setup | Native build variant + config per platform | No native setup — YAML only |
| Sync model | True event-loop/animation-scheduler hooks | Polling + retries, less precise |
| Language | JS (Jest-style test files) | YAML |
| Speed to first test | Slower (native wiring) | Fast |
| CI integration maturity | Long-established, more configuration knobs | Newer, simpler but fewer knobs |

Detox rewards investment for a large, long-lived test suite where synchronization reliability matters most. Maestro is often chosen for smaller suites or teams that want E2E coverage without taking on Detox's native build-config maintenance burden.

## Running in CI

Both need a real simulator/emulator (or, for Maestro, an actual/cloud device works too) — this is the main practical cost of E2E vs. unit tests: CI needs a macOS runner for iOS builds either way, and boot time for a simulator/emulator adds real minutes per run. This is why E2E suites are typically run on a subset of critical flows rather than exhaustively, unlike unit tests, which can cover everything cheaply.

## Key Takeaways

- E2E tests build and run the real app, catching failures (broken native build, blocking permission dialogs, hung transitions) that mocked unit tests structurally can't surface.
- Detox's core value is true synchronization — hooking into the app's event loop/animation scheduler/network layer to know when it's idle — at the cost of requiring a special native test-build variant per platform.
- Maestro trades that synchronization precision for zero native setup — YAML flows via OS accessibility APIs, with polling/retries instead of true event-loop hooks.
- Both require a booted simulator/emulator or a real device in CI, which is the main practical cost driving teams to run E2E on critical flows only rather than exhaustively.
