# React Native CLI — Platform-Specific Quirks — Permissions handling

_Last updated: 2026-08-24_

## Overview

Android and iOS use fundamentally different permission models — Android is declarative-plus-runtime-request, iOS is declarative-and-implicit — and they diverge even further in how (and whether) a user can be re-prompted after denying. This doc covers both models, the common cross-platform abstraction (`react-native-permissions`), and location as the sharpest example of the platforms converging on the same policy through different mechanisms.

## Android — declarative + runtime request, two separate steps

1. Declare in `AndroidManifest.xml`:
```xml
<uses-permission android:name="android.permission.CAMERA" />
```
2. For "dangerous" permissions (camera, location, contacts, etc. — not "normal" ones like internet access, which are granted automatically at install), also request at runtime (Android 6.0/API 23+):
```js
import { PermissionsAndroid } from 'react-native';

const granted = await PermissionsAndroid.request(
  PermissionsAndroid.PERMISSIONS.CAMERA,
  {
    title: 'Camera Permission',
    message: 'This app needs camera access to scan documents.',
  }
);

if (granted === PermissionsAndroid.RESULTS.GRANTED) {
  // proceed
}
```
The manifest declaration is necessary but not sufficient — without it, the runtime request silently fails; without the runtime request, the manifest declaration alone doesn't grant a dangerous permission.

## iOS — declarative only, requested implicitly by API use

There's no explicit "request permission" call for most iOS permissions. Instead, a usage-description string goes in `Info.plist`:
```xml
<key>NSCameraUsageDescription</key>
<string>This app needs camera access to scan documents.</string>
```
The system shows the permission dialog automatically **the first time the code actually calls the relevant API** (e.g. opening the camera). If the `Info.plist` key is missing, iOS doesn't show a generic denial — the app **crashes** on that API call. This is a harsher failure mode than Android's silent no-op, and a common App Store rejection / TestFlight crash cause when a new native dependency needs a usage string nobody added.

## The re-prompt asymmetry

- **Android**: if a user denies once, you can show your own rationale UI and call `request()` again — the system dialog reappears. Deny twice (or check "don't ask again") and the system stops showing the dialog; `request()` then resolves as denied with no UI, and the app must detect that and direct the user to Settings itself.
- **iOS**: there is **no re-prompt, ever**, after the first decision — allow or deny. Calling the API again just silently returns the previously-decided permission state. The only path back is the user going to **Settings → [App]** manually, typically launched via `Linking.openSettings()`.

Practically: any permissions UX needs to detect "denied, can't ask again" (Android) and "denied, can never ask again" (iOS, true after any first denial) and fall back to the same "open Settings" flow — but the trigger condition for that state differs by platform.

## `react-native-permissions` — the common abstraction

Bare `PermissionsAndroid` only covers Android, and iOS has no unified built-in JS API (each permission type lives in its own native module — camera, location, etc. each via their own library). `react-native-permissions` is the de facto library giving one API across both:

```js
import { check, request, PERMISSIONS, RESULTS } from 'react-native-permissions';

const permission = Platform.select({
  ios: PERMISSIONS.IOS.CAMERA,
  android: PERMISSIONS.ANDROID.CAMERA,
});

const status = await check(permission);
if (status === RESULTS.DENIED) {
  await request(permission);
} else if (status === RESULTS.BLOCKED) {
  // "can't ask again" (Android) / "denied" (iOS) — must send to Settings
}
```
`RESULTS.BLOCKED` is the library's unified name for both platforms' "no more in-app prompting possible" state — the signal to switch to an "open Settings" CTA instead of retrying `request()`.

## Location as the sharpest example of platform divergence

- **iOS**: "When In Use" vs. "Always" are separate authorization levels, and requesting "Always" up front (rather than starting with "When In Use" and upgrading later) is flagged by Apple review and often rejected. Background location additionally requires the `UIBackgroundModes` → `location` entitlement in `Info.plist`.
- **Android**: `ACCESS_FINE_LOCATION` vs `ACCESS_COARSE_LOCATION` are separate manifest permissions (precise vs. approximate). Since Android 10, background location (`ACCESS_BACKGROUND_LOCATION`) must be requested as a **separate, later** runtime request — requesting foreground and background location together in the same prompt is disallowed and Play Store review will reject it.

Both platforms converged on the same underlying policy (don't front-load the most invasive permission tier) but enforce it through different mechanisms — an authorization-level upgrade path on iOS vs. a mandatory separate request call on Android.

## Key Takeaways

- Android permissions need both a manifest declaration and a runtime request; iOS needs only an `Info.plist` usage string, with the prompt triggered implicitly by first API use.
- A missing iOS usage-description string crashes the app on first use of that API — much harsher than Android's silent failure when the runtime request is skipped.
- Android allows re-prompting until the user blocks it explicitly ("don't ask again") or denies twice; iOS never re-prompts after the first decision — both cases eventually require sending the user to Settings.
- `react-native-permissions` unifies both platforms' permission checks/requests behind one API, with `RESULTS.BLOCKED` marking the "must go to Settings" state on either platform.
- Location permissions on both platforms enforce "don't request the most invasive tier up front" — iOS via authorization-level upgrades, Android via a mandatory separate background-location request.
