# React Native CLI — Native Toolchains: iOS — Xcode build specifics

_Last updated: 2026-08-12_

## Overview

Three Xcode concepts get conflated by newcomers — targets, build configurations, and schemes — plus the question of where a given config value actually lives (Build Settings vs `Info.plist` vs entitlements), and how CocoaPods quietly patches all of this the moment `pod install` runs. This is the iOS counterpart to the Android Gradle-specifics doc.

## Targets, build configurations, and schemes — three different axes

- **Target** — a buildable product. The RN app has one main app target, but a target also exists for each CocoaPods pod (Xcode generates one target per pod inside `Pods.xcodeproj`), plus anything like a widget or notification-service extension.
- **Build Configuration** — a named set of build setting *values*. `Debug` and `Release` ship by default; more can be added (`Staging`, `QA`, etc.). A configuration doesn't build anything itself — it's a lens applied *to* a target.
- **Scheme** — the thing actually picked in Xcode's toolbar. A scheme bundles the Run/Test/Profile/Analyze/Archive actions, and each action can point at a different target+configuration combo:

```
Scheme "MyApp"
 ├─ Run      → Target: MyApp   Configuration: Debug
 ├─ Test     → Target: MyApp   Configuration: Debug
 ├─ Profile  → Target: MyApp   Configuration: Release
 ├─ Analyze  → Target: MyApp   Configuration: Debug
 └─ Archive  → Target: MyApp   Configuration: Release
```

**Android parallel:** a build variant (`debug`/`release` × flavor dimension) is roughly the Configuration equivalent, and picking a variant via `./gradlew assembleFlavorRelease` is roughly what selecting a scheme+configuration does — but Android doesn't split target/configuration as cleanly; a flavor conflates both a bit.

For a dev/staging/prod split (Android's product-flavor equivalent), the idiomatic Xcode approach isn't more targets — it's more **configurations** (`Debug-Staging`, `Release-Prod`), each wired to its own `.xcconfig` file, with one scheme per environment pointing Run at the right configuration.

## Where does a config value actually live?

| Layer | What goes here | Example |
|---|---|---|
| **Build Settings** | Compiler/linker-level config, resolved per target+configuration | `PRODUCT_BUNDLE_IDENTIFIER`, `CODE_SIGN_STYLE`, optimization level (`-O0` vs `-Os`) |
| **Info.plist** | App metadata read at *runtime* by iOS | Permission usage strings (`NSCameraUsageDescription`), URL schemes, display name |
| **Entitlements file** (`.entitlements`) | Capabilities granted by Apple, checked at install/runtime | Push notifications, Keychain sharing, App Groups, Associated Domains |

The catch: `Info.plist` values can reference Build Settings via `$(VARIABLE_NAME)` interpolation. `CFBundleDisplayName` might literally be `$(APP_DISPLAY_NAME)`, with the actual value defined per-configuration in Build Settings (or an `.xcconfig`) — this is how the app name/icon can differ per environment without hand-editing `Info.plist` per build.

Entitlements aren't tunable config in the same sense — they're a request to Apple that has to match what's actually provisioned in the provisioning profile (ties into signing).

## `.xcconfig` files — text-file build settings

An `.xcconfig` is a plain-text key-value file:

```
// Config-Staging.xcconfig
API_BASE_URL = https:/$()/staging.api.example.com
APP_DISPLAY_NAME = MyApp (Staging)
PRODUCT_BUNDLE_IDENTIFIER = com.example.myapp.staging
```

(The `$()` avoids Xcode reading `//` as a comment start.)

An `.xcconfig` file is assigned to a **configuration**, per target, in the project's Info tab. Reasons to use one over typing values into the Build Settings UI:

- **Diffable in git** — Build Settings live inside the giant `project.pbxproj` blob; `.xcconfig` files are clean text.
- **Composable** — an `.xcconfig` can `#include` another one, layering a `Common.xcconfig` with per-environment overrides on top.
- **CI-friendly** — easy to template or swap without touching the Xcode project file at all.

**Android parallel:** functionally close to what `gradle.properties` + flavor-specific `build.gradle` blocks do — externalizing environment-specific values outside the main project file.

## How CocoaPods wires into the Xcode build

![Diagram showing pod install generating Pods.xcodeproj from the Podfile, then writing Pods-App debug/release xcconfig files (included into the app target's build settings) and adding CP-prefixed build phases (check manifest lock, embed frameworks, copy resources) to the app target, making it pod-aware before being bundled with Pods.xcodeproj into the .xcworkspace](../../Assets/ios_xcconfig_injection.svg)

When `pod install` runs, CocoaPods:

1. Reads the `Podfile`, resolves versions, writes `Podfile.lock`.
2. Generates **`Pods.xcodeproj`** — a separate Xcode project with one target per pod, plus an umbrella "Pods" aggregate target.
3. Generates the **`.xcworkspace`** containing both the app project and `Pods.xcodeproj` side by side — the reason `.xcworkspace` becomes mandatory the moment there's any pods.
4. Injects generated `.xcconfig` files into the app target — `Pods-App.debug.xcconfig` / `.release.xcconfig` — setting header search paths, `OTHER_LDFLAGS`, `FRAMEWORK_SEARCH_PATHS`, so the app target's compiler can find and link the pods.
5. Adds `[CP]`-prefixed build phases to the app target: `[CP] Check Pods Manifest.lock`, `[CP] Embed Pods Frameworks`, `[CP] Copy Pods Resources`. The manifest-lock check is the one that fails loudly (correctly) if `Podfile.lock` and the installed Pods dir have drifted — the classic "forgot to run `pod install` after pulling" error.

Because CocoaPods regenerates its `.xcconfig` files on every `pod install`, hand-editing them directly is fragile — anything permanent belongs in the `Podfile` (via a `post_install` hook) or a separate `.xcconfig` the project owns, not the generated one.

## Key Takeaways

- Target, Configuration, and Scheme are three orthogonal axes — a scheme maps each action (Run/Test/Archive/…) to a target+configuration pair, it doesn't build anything on its own.
- A given setting can live in Build Settings, `Info.plist`, or an entitlements file — and `Info.plist` can pull values from Build Settings via `$(VAR)` interpolation, which is how per-environment app names/bundle IDs work without editing `Info.plist` per build.
- `.xcconfig` files externalize Build Settings into diffable, composable, CI-friendly text files — assigned per target/configuration.
- `pod install` doesn't just generate `Pods.xcodeproj` — it also patches the app target directly, injecting `.xcconfig` includes and `[CP]` build phases. Those generated files get overwritten on every `pod install`, so permanent changes belong in the `Podfile`, not hand-edited into them.
